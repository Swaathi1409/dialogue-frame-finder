MY UNDERSTANDING OF THE PROBLEM

We are given a video URL and a target dialogue line. The goal is to automatically find the first exact video frame where that dialogue becomes visually visible on the screen, and return the frame image, timestamp, frame number, and recognized text.

The important point is that this is not simply a speech recognition problem. The moment a person says the sentence can be different from the moment the subtitle or dialogue appears visually. So speech recognition can help locate the approximate part of the video, but the final answer has to come from examining the actual video frames.

I understood the problem as having two main stages. First, where should I search. Second, which exact frame is the first visual appearance.

For the first stage, ASR such as faster whisper can be used to locate approximately where the dialogue occurs. ASR is therefore a localization tool, not the final detector.

For the second stage, OCR is used on the actual video frames. The system first samples the candidate region, checks for the target dialogue, and then performs a finer search backward to identify the earliest frame where the text is present.

OCR can make small mistakes, such as confusing characters, so exact string matching is not enough. Normalized text and fuzzy matching are needed so that small OCR errors do not cause a real match to be missed.

The system also needs to handle uncertainty. A result should not be accepted just because OCR matched once. Factors such as OCR similarity, OCR confidence, whether the same text continues to appear in nearby frames, and whether ASR also indicates the same region should all be considered. If the evidence is not sufficient, the system should explicitly say not found instead of guessing.

Overall flow I understood: video URL and target dialogue go in, the video is downloaded, audio and video are extracted, ASR finds a rough location, a candidate time window is formed, OCR samples that region, the coarse to fine frame search finds the first visual occurrence, confidence and persistence are checked, and the timestamp, frame number, extracted text, and frame image come out.

The main engineering idea taken from the research is to use speech to reduce the search space, and use the actual video pixels to prove the answer. This is why we should not simply run OCR on every frame of the entire video. That could work, but it would be unnecessarily expensive and would not show an intelligent way of locating the relevant portion. A coarse to fine search is more efficient, explainable, and easier to defend.

Python was chosen because the required video, ASR, OCR, matching, and testing tools all have strong Python support. The proposed stack is yt dlp for video acquisition, faster whisper for coarse temporal localization, PaddleOCR to read text from frames, RapidFuzz to match it, pytest for testing, and a simple CLI application rather than an unnecessarily complex web application.

I also understood that these specific technologies are design choices, not requirements directly stated in the assignment. The actual requirement is to correctly identify the first visual frame, extract the dialogue, provide the required outputs, handle normal variation and uncertainty, and be able to explain and defend the solution.

Discovery, matcher false positive with repeated words

What I typed
I described a video with lines like run slow, run fast, run angry, and run tired, and said that when the input was run tired, the tool incorrectly detected the first occurrence of run and skipped past tired, giving the wrong timestamp and frame, and asked for this to be fixed and for other edge cases to be checked too.

Cleaner version
Fix the false positive in matcher.py caused by partial ratio scoring, where run tired incorrectly matches run slow due to the shared word run at the start. What happened
The root cause was that plain partial ratio finds the best same length alignment inside a string, so run tired at nine characters aligned strongly over run slow at eight characters because they share the prefix run, producing a score above the matching threshold. A word boundary check was added for short one or two word targets so that run cannot match inside running or runner. A word coverage gate was added for multi word targets requiring most of the target's words to individually appear in the OCR text, which blocks run slow from matching a target of run tired since tired is missing. A tie handling threshold was also added in the localizer so that when several ASR segments score close to each other, the later segment is preferred, avoiding anchoring on an early generic occurrence of a shared word. What happened
Investigation showed that even with cookies present and a JS runtime installed to handle challenge scripts, YouTube and Instagram both strictly block requests coming from known datacenter IP ranges, which includes typical cloud hosting providers. YouTube compares the residential IP address where the cookies were originally generated against the datacenter IP now using them, and invalidates the session immediately for security reasons. The conclusion was that free cloud deployments cannot reliably download YouTube or Instagram videos without a paid residential proxy service, and the practical recommendation was to run the project locally on a personal computer, where the residential IP address naturally avoids this block.

ITERATIONS AND CORRECTIONS

Phase 1, ffprobe replaced with OpenCV. The original brief called for real fps through ffprobe, but ffprobe is not bundled with imageio_ffmpeg on this machine. OpenCV reads the same values directly, so it was used instead, and the variable frame rate limitation this introduces is documented directly in frame_extractor.py.

Phase 1, imageio ffmpeg added to requirements.txt. The original brief assumed a system installed ffmpeg binary would be available, but it was not present on this machine, so the imageio_ffmpeg package was added as a dependency instead.

Phase 1, ffmpeg location bug in downloader.py. The versioned ffmpeg binary name was not being found by yt dlp, and this was fixed by copying it to a temporary directory under the plain expected name.

Phase 3, PaddleOCR version pinned. Version 3.x of PaddleOCR crashes on Windows CPU, so the dependency was pinned to version 2.7.3 together with paddlepaddle 2.6.2.

Phase 6, partial ratio minimum length guard added. A single character OCR result was scoring 100 against an unrelated phrase, so a thirty percent length guard was added inside matcher.score, later tightened further to fifty percent after a related issue surfaced again during real world testing.

Phase 7, matcher scoring changed from plain partial ratio to a combined approach. Repeated words across different captions, such as run appearing in run slow, run fast, run angry, and run tired, were causing false positives. The scoring was changed to combine partial ratio with token set ratio, then further refined into two modes depending on whether the OCR text looks like a standalone caption or a longer block of text, along with a word level coverage gate and a word boundary check for short targets.

Phase 7, ASR tie handling added. When multiple transcript segments scored close to each other, the localizer was anchoring on the earliest one. A tie threshold was added so the later matching segment is preferred instead, which better matches how repeated dialogue actually appears in a video.

Discovery phase, YouTube JS runtime setting removed. Adding a node based JS runtime option to suppress a deprecation warning had the unintended side effect of forcing yt dlp to select a player client that requires sign in, breaking previously working downloads. The setting was removed entirely once this was traced.

Discovery phase, OK.ru download strategy changed twice. The first fallback attempt used a third party Vercel based API, which was later found to return CDN links locked to the Vercel server's own IP address and therefore not usable from this machine. This was replaced with a Playwright based Chromium fallback that captures the real CDN URL from a genuine browser session instead.

Discovery phase, deployment approach reconsidered. After confirming that cloud hosting providers are blocked at the IP level by YouTube and Instagram regardless of cookies, local execution using a cloned repository was established as the recommended way to run and evaluate the project.
