Discovery during Phase 1 - ffmpeg binary name issue

what I typed:
nothing - hit this bug while wiring yt-dlp

what happened:
yt-dlp needs ffmpeg to merge separate video and audio streams (which is
how OK.ru and YouTube both work). imageio_ffmpeg bundles the binary but
names it with the platform and version like ffmpeg-win-x86_64-v7.1.exe.
yt-dlp looks for a file named exactly ffmpeg or ffmpeg.exe and does not
find the versioned name. fixed by copying the bundled binary to a temp
folder with the plain name once per process. added _get_ffmpeg_dir() in
downloader.py to handle this.

note: design change from the original plan so logging it here.


ITERATIONS AND CORRECTIONS

ffprobe replaced by OpenCV for video info
the spec said "real fps via ffprobe" but ffprobe is not included in the
imageio_ffmpeg package, only ffmpeg is. rather than add another dependency,
i used OpenCV's VideoCapture to read fps, frame count, duration and
resolution. it uses the same underlying library as ffprobe so the values
are the same. the only real limitation is variable frame rate video, which
OK.ru content is not. documented this in frame_extractor.py.

imageio-ffmpeg added to requirements.txt
the original requirements assumed ffmpeg would be on the system PATH.
it wasn't in this environment. imageio_ffmpeg bundles the binary so users
don't have to install ffmpeg themselves. added it to requirements.txt.

ffmpeg_location bug in downloader.py
first attempt passed the imageio_ffmpeg binary folder to yt-dlp as
ffmpeg_location. yt-dlp looks for the name ffmpeg.exe in that folder and
doesn't find the versioned filename. fixed by copying to a temp dir under
the plain name. see the Phase 1 discovery entry above.

Discovery during Phase 2 - apostrophe handling in normalize()

what I typed:
nothing - found during test run

what happened:
wrote a test expecting normalize("It's ALIVE!") to return "its alive".
it actually returns "it s alive" because the apostrophe is treated as
punctuation and replaced with a space like any other non-word character.
the normalize() behavior is actually correct for our use case - partial_ratio
handles the extra space fine. fixed the test expectation, not the code.
added a comment explaining why this is fine.

note: logged because it was a real bug found in the test, not the code.
the fix was one line in the test file.
