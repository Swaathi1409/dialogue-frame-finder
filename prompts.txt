MY UNDERSTANDING OF THE PROBLEM

We are given a video URL and a target dialogue line. The goal is to automatically find the first exact video frame where that dialogue becomes visually visible on the screen, and return the frame image, timestamp, frame number, and recognized text.

The important point is that this is not simply a speech recognition problem. The moment a person says the sentence can be different from the moment the subtitle or dialogue appears visually. So speech recognition can help locate the approximate part of the video, but the final answer has to come from examining the actual video frames.

I understood the problem as having two main stages. First, where should I search. Second, which exact frame is the first visual appearance.

For the first stage, ASR such as faster whisper can be used to locate approximately where the dialogue occurs. ASR is therefore a localization tool, not the final detector.

For the second stage, OCR is used on the actual video frames. The system first samples the candidate region, checks for the target dialogue, and then performs a finer search backward to identify the earliest frame where the text is present.

OCR can make small mistakes, such as confusing characters, so exact string matching is not enough. Normalized text and fuzzy matching are needed so that small OCR errors do not cause a real match to be missed.

The system also needs to handle uncertainty. A result should not be accepted just because OCR matched once. Factors such as OCR similarity, OCR confidence, whether the same text continues to appear in nearby frames, and whether ASR also indicates the same region should all be considered. If the evidence is not sufficient, the system should explicitly say not found instead of guessing.

Overall flow I understood: video URL and target dialogue go in, the video is downloaded, audio and video are extracted, ASR finds a rough location, a candidate time window is formed, OCR samples that region, the coarse to fine frame search finds the first visual occurrence, confidence and persistence are checked, and the timestamp, frame number, extracted text, and frame image come out.

The main engineering idea taken from the research is to use speech to reduce the search space, and use the actual video pixels to prove the answer. This is why we should not simply run OCR on every frame of the entire video. That could work, but it would be unnecessarily expensive and would not show an intelligent way of locating the relevant portion. A coarse to fine search is more efficient, explainable, and easier to defend.

Python was chosen because the required video, ASR, OCR, matching, and testing tools all have strong Python support. The proposed stack is yt dlp for video acquisition, faster whisper for coarse temporal localization, PaddleOCR to read text from frames, RapidFuzz to match it, pytest for testing, and a simple CLI application rather than an unnecessarily complex web application.

I also understood that these specific technologies are design choices, not requirements directly stated in the assignment. The actual requirement is to correctly identify the first visual frame, extract the dialogue, provide the required outputs, handle normal variation and uncertainty, and be able to explain and defend the solution.

## 0. Project Goal

Build a Python CLI tool that, given a video URL (example domain OK.ru) and a target dialogue line, finds the first video frame where that dialogue is visually displayed on screen as burned in text, and reports:

- the frame image, saved as PNG
- the timestamp in seconds, computed from the real fps of the video
- the frame number
- the OCR recognized text
- a confidence level, High or Low or Not Found, with the reasoning behind it

This is a visual appearance detector, not a speech detector. Speech timing from ASR is only used to narrow down where to look. Only OCR, which reads pixels, can prove text is actually visible on screen at a given frame.

## 4. Algorithm

Stage 0, acquire. Download the video with yt dlp. If the download fails for any reason, network, extractor breakage, region lock, stop with a clear error. Do not proceed on a partial or failed download.

Stage 1, coarse localization with ASR. Extract audio with ffmpeg. Run faster whisper to get word level timestamped segments. Fuzzy match the target dialogue against the transcript with RapidFuzz. Take the best matching segment's time range and pad it, roughly minus 3 seconds to plus 8 seconds by default, configurable, to get a candidate search window. The padding exists because on screen captions can lag or lead the spoken line, or the line might not be spoken at all.

Stage 2, fallback window. If nothing in the transcript matches well enough, fall back to a fixed interval OCR scan, roughly every 1 to 2 seconds, across the whole video. Slower, but bounded and guarantees the tool still tries.

Stage 3, coarse to fine frame search inside the window. Sample frames inside the window at a moderate rate, roughly every 0.5 seconds. Run OCR on each sampled frame and fuzzy match against the target line. Find the first sampled frame that clears the match threshold. Then binary search backward between that frame and the last non matching frame, narrowing down to native frame granularity, to find the exact first frame. Then check a couple of frames after it to confirm the match holds, to rule out a single frame OCR misread.

Stage 4, report. Frame number, timestamp computed as frame number divided by real fps, OCR text, confidence bucket with the reasoning, and the saved frame image. If nothing clears even the low confidence threshold anywhere, including the fallback scan, return an explicit not found result. Never guess.

## 5. Confidence Model

Signals used: the RapidFuzz match score on normalized text, PaddleOCR's own per detection confidence, whether the match persists across neighboring frames, and whether ASR roughly agreed on timing as a soft bonus signal.

Buckets, kept as named constants in config.py so they are easy to tune later:
- High confidence: match score 90 or above and the match persists across neighboring frames. Report normally.
- Low confidence: match score between 70 and 90, or a single frame flicker with no persistence. Report the best candidate but clearly flagged as low confidence, with the reasoning stated.
- Not found: nothing clears even the low threshold anywhere. Report not found explicitly.

State clearly in APPROACH.md that these thresholds are engineering heuristics chosen by judgment, not numbers derived from a statistical study.

## 10. Reference, Rejected Alternatives, for APPROACH.md

- OCR every frame, correct but far too slow to be practical on longer videos
- ASR only, wrong signal, proves speech was said, not that text is visible on screen
- Subtitle track extraction as the primary path, most target videos including the OK.ru example have no extractable subtitle track, kept as an opportunistic mention only
- PySceneDetect or scene cut detection as the core mechanism, on screen text over a static background is not a scene cut, this would miss the exact event
- A vision language model watching the whole video, expensive, unpredictable, and hard to explain frame exact reasoning from
- EasyOCR as the primary OCR engine, benchmarked slower and less accurate than PaddleOCR on this kind of overlay text
- WhisperX or similar phoneme level aligners, unnecessary precision, OCR already does the fine grained work
- A web server, database, queue, or microservices, this is a single run batch CLI tool, none of that complexity is justified
